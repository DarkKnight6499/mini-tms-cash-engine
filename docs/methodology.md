# Methodology and supported profiles

This library is an offline prototype workflow built around seeded synthetic data. It demonstrates reconciliation, cash planning and control design. It is not a replacement for a commercial treasury system. Bank names, account identifiers, counterparties, cash flows and FX quotes are synthetic.

## Data lineage and money

`synthetic.generate()` uses `numpy.random.default_rng` with the seed exported in `results.json`. It creates four legal entities, three currencies, eight accounts at three synthetic banks and ninety calendar days of booked activity. There are three currency concentration accounts, disbursement and collection children, and a local account. Separate clean and defective statement exports contain the same underlying history. The defective copy repeats a receipt, changes a closing balance and removes a statement day. These are controlled defects, not random simulated failures.

The normalized ledger includes entity, bank, account, currency, value date, booking date, signed amount, type code, reference and running book balance. It also retains statement identity and description. Statement balances are separate so that statements without transactions retain their cash information. Account ownership comes from the supplied account registry, not from an inferred XML narrative.

Statement amounts and payment controls use integer cents. `cents()` rejects nonfinite amounts and fractional cents rather than rounding. Public DataFrames express money in currency units for analysis. Expected forecast amounts and FX conversions use floating point. Their reconciliation tests allow numerical precision errors; they do not accept a material cash residual.

## Primary format verification

The following original specification texts were opened and their indicated sections read during the continuation audit. These sources establish field semantics. The implementation deliberately supports a narrower profile than the complete standards.

ISO: OPBD and CLBD represent opening and closing booked balances. Entry direction and status distinguish credits, debits and booked entries. Verified against the original ISO Payments Maintenance Message Definition Report, September 2009, [original ISO endpoint](https://www.iso20022.org/message/mdr/12666/download/111), read from the [copy hosted by Payments Services Austria](https://zv.psa.at/schemata/Payments_Maintenance_2009.pdf). camt.053.001.02: section 2.26, printed pages 158 to 159, and sections 2.79 to 2.83, pages 172 to 173. pain.001.001.03: structure on pages 710 to 714, including group controls 1.6 and 1.7, payment controls 2.4 and 2.5, execution date 2.17, debtor account and agent 2.20 and 2.21, and transaction fields 2.27 to 2.43. The [ISO archive](https://www.iso20022.org/catalogue-messages/iso-20022-messages-archive?search=pain.001.001.03) confirms the payment version; its unfiltered catalogue also lists the statement version. The ISO report endpoint timed out during this audit; the readable copy is the ISO-authored report, not a third-party summary.

BAI2: controls sum status, summary and unsigned detail amounts. Record counts include continuations. Nontext continuations replace a slash with a comma; narrative continuations concatenate text. Verified against the [BAI Version 2 Technical Reference Manual](https://www.bai.org/docs/default-source/libraries/site-general-downloads/cash_management_2005.pdf), Record Formats sections 03, 16, 88, 49, 98 and 99, Data Elements: Account Control Total, and Appendix A. Codes 010 and 015 identify opening and closing ledger balances; 195 and 495 identify incoming and outgoing money transfers. The continuation audit corrected the serializer and parser together and added hand-calculated continuation tests.

MT940: the implemented fields are transaction reference, account, statement sequence, final opening balance, statement lines, narrative and final closing balance. Decimal commas, optional entry dates and RC/RD reversal signs were checked in [Danske Bank's MT940 structured format description](https://danskeci.com/-/media/pdf/danskeci-com/swift-mt/reconciliation/mt940_structured.pdf), Field Information: 20, 25, 28C, 60F/M, 61, 86 and 62F/M, pages 3 to 12. This is an originating bank's public description. Direct [SWIFT Category 9 documentation](https://www2.swift.com/knowledgecentre/publications/us9m_20230720/2.0) was inaccessible. Full SWIFT conformance remains unverified.

### Supported ingestion subsets

- camt.053.001.02: namespace-aware XML, account `Othr/Id` or `IBAN`, account currency, OPBD and CLBD, BOOK entries, explicit booking and value dates, date or datetime choices, and a single transaction detail per entry. The entry sign already reflects a reversal, so no second sign inversion is applied. Multiple detail allocations are rejected. Generated bank codes use the proprietary branch.
- BAI2: file, group, account, detail and trailer envelopes; continuation records; update group status with a final daily modifier; defaulted or immediate funds types for summary and detail; defaulted funds fields for status; opening and closing status codes; signed status amounts and unsigned monetary details. Debit direction follows the documented code range. The parser does not maintain the full code catalogue. Complex funds distributions, loan codes and nonmonetary detail are rejected. Both normalized dates use the group as-of date because this profile supplies no separate value date. YYMMDD means a year in the current century, from 2000 through 2099. The text profile uses one physical record per line and currencies with two decimal minor units. Files are treated as independent daily snapshots; stateful update replacement, deletion and correction processing are omitted. Group status and modifier semantics were checked in Data Elements: Group Status and As-of-Date Modifier of the BAI manual.
- MT940: bare statement bodies, without FIN transport blocks, using the final balance fields. Transaction lines support optional funds codes and entry dates, plus RC and RD reversals. A missing entry date uses the value date. Entry year uses the closest valid date around the value year, including a year boundary. Narrative continuations are retained. Interim balance pages and bank-specific structured narrative interpretation are outside scope.

Detected malformed or unsupported profile syntax raises `ValueError` and yields no partially accepted file. Unknown accounts and currency mismatches also fail ingestion. These parsers are not complete schema validators: optional camt elements outside the extracted profile may be ignored, and no full BAI code catalogue or MT940 transport validator is included. Business reconciliation findings return a table with format, statement identity, account, date, code and detail.

## Reconciliation and quarantine

For every statement, opening plus signed movements must equal closing exactly in cents. Repeated account/day statements, repeated references within an account, missing references and consecutive-day opening/closing discrepancies are findings. A reference is assumed unique for its account over the ingestion batch. Banks that recycle references need a different matching policy.

Expected dates and accounts are supplied explicitly. The example expects calendar-day statements including weekends, so a missing weekend is a defect in this dataset. Production bank calendars would need separate configuration. The expected dates iterable is materialized so a generator works across multiple accounts.

Every statement with a finding is excluded from `clean_ledger` and valid position balances. Raw ledger rows remain available for investigation. A duplicate statement quarantines both copies. Account controls quarantine the account statement; an invalid group or file control conservatively quarantines the complete file. Nothing silently repairs an out-of-balance closing value.

The quality report contains two residuals, a duplicate reference, a balance discontinuity on the following day and a missing day. The discontinuity produces a third quarantined statement. Later valid closing balances can reestablish a position snapshot; the missing period still has incomplete transaction coverage. This is a snapshot acceptance policy, not a claim that the historical ledger has been repaired.

## Cash position, sweeps and pooling

For each account and day, position uses the latest accepted booked closing balance. An absent current statement marks the balance stale and records its source date. An account without a prior valid balance remains unknown rather than zero. Aggregation preserves unknown balances. FX conversion uses exact-date quotes of USD per currency unit. Cross rates divide native and reporting quotes. Missing, duplicate or nonpositive rates are rejected.

Target surplus equals balance less target. The sweep simulation moves each eligible child's surplus to its same-currency concentration account; a negative surplus funds the child from the concentration account. Zero targets implement zero balancing. Transfers identify different legal entities as intercompany. Native cash is conserved separately for each currency. Sweeps require fresh balances and may create a concentration overdraft. No fee, credit limit or legal eligibility test is included. Sweeps are a separate scenario; the baseline forecast retains entity balances before the sweep.

Notional compensation converts balances to USD equivalents while leaving actual account balances unchanged. Positive balances earn the stylized credit rate; negative balances incur the stylized debit rate. Compensation matches the cheapest deposits against the most expensive borrowing only when the borrowing rate exceeds the deposit rate. Each matched amount benefits by the avoided borrowing rate less the displaced deposit rate, multiplied by days divided by 365. The example holds the latest snapshot, quotes and rates constant over the forecast horizon. This is not daily realized interest or a contractual multicurrency pooling product. Tax, set-off rights, cross-guarantees, currency haircuts and execution costs are omitted.

## Direct cash forecast

Weeks are zero based internally. The horizon starts on the day after the statement history and uses successive seven-day windows, without a holiday calendar. AR due dates match their synthetic aging buckets. Expected receipts equal invoice amount multiplied by collection probability and timing weight. Timing weights sum to one, while collection probabilities may be below one. Delays are allocated relative to the later of due week and the first forecast week. Uncollected amounts and allocations after the horizon are not redistributed into earlier weeks.

AP invoices are paid in their due week; overdue AP falls into the first week. Payroll, tax, debt service and matched intercompany legs use explicit scheduled dates. Foreign flows use spot frozen at forecast inception. Each entity's closing equals opening plus receipts, vendor outflows, payroll, tax, debt service and intercompany flows. The following week's opening equals that closing. A buffer breach means closing is strictly below the entity's stylized USD buffer. The model does not automatically borrow to fix a shortfall.

Actuals are a separately labelled synthetic scenario using seeded perturbations, lower receipts, higher vendor outflows and a receipt shift between the first two weeks. Intercompany actuals conserve group cash. These synthetic actuals are not observed bank transactions or an out-of-sample accuracy study.

Variance equals actual less forecast. Positive variance improves cash relative to plan, whether through larger receipts or smaller outflows. Bias is the mean signed variance per line; total variance is the sum. MAPE is the mean absolute variance divided by absolute actual, excluding zero actual denominators. WAPE uses total absolute error divided by total absolute actual. Coverage counts and missing actual counts are reported. Missing actuals stay unknown and do not become zero. An actual-only line uses a zero forecast. Largest error explanations describe patterns and explicitly label causes as hypotheses.

## FX recommendations

Foreign forecast flows are netted by entity, currency and tenor bucket relative to the entity's functional currency. Signed hedge notional equals negative exposure multiplied by the policy target. Residual exposure equals exposure plus hedge. Bands validate the target ratio; they are not regulatory requirements. Functional-currency flows are excluded.

For spot quoted as domestic units per foreign unit, the stylized forward is spot multiplied by `(1 + domestic_rate * days / 365) / (1 + foreign_rate * days / 365)`. Forward points are forward less spot. This simple-interest parity calculation omits spreads, basis, collateral, credit risk and transaction costs. Tenor buckets use representative maturity days, not invoice-level maturity matching. Gross absolute exposure totals sum the absolute net exposure in each bucket, so they differ from a net group currency position. No real hedge trades are executed.

## Maker-checker and payment validation

Creation requires a configured maker identity. Approval requires a configured checker identity distinct from the maker. A single-currency batch below the stylized threshold needs one checker; a batch at or above it needs two distinct checkers. The threshold applies to the total native batch amount. Export requires approval and is allowed once per in-memory batch identifier. Frozen payments and batches, plus a stored payload digest, prevent ordinary edits and detect payload changes after creation. A failed action does not add an audit event.

Each frozen audit event hashes its sequence, timestamp, action, actor, batch identity, payload digest and previous event hash using canonical JSON and SHA-256. Creation and approvals bind the batch payload. Export binds the XML bytes. Snapshot properties expose tuples, and there is no edit or delete API. Verification detects edits, reordering and middle deletions. An externally retained head or count detects tail truncation. Without an external checkpoint, a valid prefix remains a valid chain. This is application-level append-only behavior, not tamper-proof storage against a privileged Python process. Roles are asserted identities, not authenticated users. Concurrent access, persistence, digital signatures and bank acknowledgements are omitted.

The payment file uses a single payment-information block with other-account identifiers, a synthetic BIC and credit transfers. The structural validator checks namespace, sequence, cardinality, scalar shapes, field lengths, dates, positive amounts, unique payment identifiers, currency consistency, both control sums and both transaction counts. It can compare the complete parsed payload against the approved batch. It intentionally rejects valid ISO variants outside this narrow profile.

### XSD limitation and retrieval attempts

The ISO archive's pain.001.001.03 XSD link and complete message-set downloads were attempted through the web tool. They returned unsupported octet-stream and ZIP content types. The [pain XSD endpoint](https://www.iso20022.org/message/14316/download) and original ISO report were also attempted using `curl` with a browser user agent; the offline shell could not connect. No published XSD copy was obtained, and no XSD validation is claimed. `tests/fixtures` contains hand-written minimal statements and a provenance note, not a substitute schema. The original ISO message definition report was read through the Payments Services Austria copy and supplied the field verification above. Direct SWIFT documentation also failed, so MT940 verification uses the bank's public description.

All interest rates, forward rates, collection probabilities, hedge bands, liquidity buffers and approval thresholds are illustrative assumptions. The corporate extensions separately identify the verified reserve-ratio default and scoped Rule 10b-18 constants. See the formulas, source paragraphs, provenance and limitations in [README](../README.md).
